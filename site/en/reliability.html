04 / resilience

Cut off,
is not amnesia

One full day without reaching the hub, and the local node keeps distilling on the staged data, in small batches. Five days without recovery, and it acts as its own hub. When the hub comes back, the two sides merge in a fixed order: push → send back → confirm → pull snapshot, with no step skipped. Only when the last step succeeds and the local copy is still there does the staging get deleted.

02

Merging back has one order only

Push rows written locally (push), then send back the rows accumulated while offline (rows), and pull a new snapshot (pull) only after the hub confirms. If a step fails, the next one does not run and the local copy is not deleted; the next round sends the same batch again, the hub recognises it and does not write duplicates. Session reads work the same way: when the hub is unreachable, fall back to the local copy and mark the receipt source=local + degraded, never passing local results off as the hub's.

03

A backup does one thing: catch up

A backup catches up entry by entry along the replication sequence. Behind, it catches up; missing entries, it reports "unavailable + gap" rather than passing off stale content. Only after catching up and passing verification may it take over.
